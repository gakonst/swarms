# Swarms

Crowdfunded AI agents that research and build in the open, on the Tempo gateway (https://gateway.tempo-dev.workers.dev): anyone starts a swarm with a goal (a question to answer, software to build or port, data to gather, a guide to write), funds it by sending it USDC.e, pathUSD, OUSD or MACH, and can contribute to an existing swarm or lend a machine. Swarm World makes the work visible. It uses only the gateway's public HTTP API, as any outside developer would, so it also tests that API.

- Streaming instead of polling, in the browser (2026-11-07, the user's request: "reduce the need for polling as well when a system can be instead streaming"; the plan is polling.txt of the same day's audit, items 3, 4, 6, 7 and 8):
  - One room socket per swarm per tab (`wire.ts`): the swarm page, the room, the roster (`useRoster`), the transcript, the side pane, Machines and the Code tab all join it, and it stays open 5 s after the last of them leaves, so a tab switch or a back navigation reuses it. `/s/:id/code` opens its own with `?listen=1`, which the server must pass to the swarm object and leave out of presence.
  - The client counts the socket as streaming only once `welcome` arrives. Until then (at most 4 s), or on a server that never sends it, every fallback poll keeps running, so this client works against the Worker before it.
  - `pulse` is merged into the detail with no request (`usePoll` now also returns `set`), `artifacts` and `roster` replace their lists, and `changed` refetches only the parts it names: detail (`?feed=0`), feed (one `?after=` read when `/live` is closed), members (the room's `chat?after=`, which also refreshes `me`), branches, roster, hands (the lent hands and the machine list), code (the snapshot, and one git log read on `/s/:id/code`) and artifacts. A hidden tab holds the parts and fetches each once when it is shown again.
  - A `welcome` after a reconnect, or whose version differs from the last one the tab applied, refetches every part once; an unchanged part answers 304. On a first visit the parts are read at mount and again at the first welcome; data the page already had (memory, session storage or the server render) waits for the welcome instead.
  - Fallback polls run only while the socket is down: the detail every 10 s, the room every 15 s (once a minute while its socket is open without a welcome, as before), the feed every 5 s while running and 10 s otherwise, the artifacts, branches and roster every 60 s, the code log every 60 s while the tab is visible. While it streams: the branches every 60 s only while the swarm runs (a branch's spending has no push), the lent hands every 60 s while Machines is open (their requests and charges have no push), and the machine list at most every 10 s, and only after new machine, tool or output entries arrived. Everything else waits for a message.
  - `usePoll` no longer fetches when its pace changes: the next fetch is due at the last one's start plus the new pace, `null` pauses it, and `reload` fetches at once, after a fetch already in flight. Before, every pace change (running to paused, stream up or down) fetched immediately.
  - `/live` is always followed with `?after=` (the page used nothing else, and the other branch is gone from `api.ts`). `useLive` is one state, off, following or live with its streams, where it kept `pushed` and `connected` flags that disagreed after an idle frame. The feed is not polled while `/live` is open: it delivers every entry with its seq and replays the gap on reconnect. A stream that delivered entries or lasted 30 s reopens at once; one that failed sooner waits 3 s.

  - Waking is one rule (`Phase.wakes`): a pause for money or before any funding wakes on new money, a pause for one costly request (`costly`) or after three failed turns (`rest`) wakes on new money or a note, and a money pause also wakes when a resting source comes back (`Phase.due`). Waking moves the run to `waiting` and sets the alarm, and `costly` is forgotten then, so a turn tries again; there is no timed cooldown (the user's decision). Before, a room note woke only a swarm D1 said was running, so a `rest` pause ignored notes despite its own sentence, and `costly` stayed until a turn completed, which no turn could do: 48dfb55dc725 had been paused `costly` since 2026-11-06 15:52 with $0.314 left. `heal` arms an alarm for a waiting, starting or working run that has none, at most every 5 minutes, and never for a paused one, where it used to re-step every paused swarm (fund, refresh, pause: about five subrequests) every 5 minutes while anyone viewed it. `alarm` never pushes back an earlier alarm set during the step, so money that arrives while a step runs is acted on at once instead of at the step's own next time (up to 10 minutes).
  - Starting a turn is idempotent: the run records `starting` with the id `<agent>:<n>` before `POST /v1/agents/:id/turns` (the gateway's turn `id`), and a 409 for that id counts as already started, so an object that resets between the call and its bookkeeping no longer queues a second turn the swarm does not track.

## API and MCP

- Every operation lives in `Operations` as a function of `(env, input)` returning a `Problem.Result`. The web app's `/api` routes, the public `/v1` routes (`Rest`) and the MCP tools (`Mcp`) are thin adapters over these functions, so validation, errors and side effects match on every surface. That includes transfers (`contribute`, `transfer`), which `/v1` serves under `/v1/swarms/:id/contributions`, and the wallet a swarm from before 0003 gets on its first read. Each operation parses its own input with Zod, and the schemas have no transforms: the MCP SDK validates a tool's arguments with the same schema and passes on the parsed value, so a transforming schema (the pledge amount to atomic units) failed when the operation parsed that value again.
- Every page reads only what the public API serves (the user's request of 2026-11-02, so anyone can build another UI or scrape it): `/v1` has everything `/api` does, plus `GET /v1/problems` (the idea bank, each problem marked open or with the swarm on it), `GET /v1/swarms/:id/machines` (`Fleet.fleet` over the feed and the lent hands: the Machines tab, with each machine's settings and command history) and `GET /v1/swarms/:id/backers` (the Ideas tab: ideas ranked by money and every backer), with MCP tools for each (`problems_list`, `swarm_machines`, `swarm_backers`).
- State machines made explicit so bad states cannot happen: `Swarm.fund` is single-flight (`funding`), so two swaps of one balance never run at once; the Fund component cannot pay again after a payment until Fund again is tapped; Lend your machine is a `Step` union (closed, naming, issuing, failed, issued).
- Pages render on the server and stream (the user's request of 2026-11-02). `src/worker/Page.ts` answers `/`, `/join`, `/new`, `/about`, `/docs` and `/s/:id` for HTML requests (listed in `run_worker_first`). It writes the head of `index.html` at once, then the page's own title, description and Open Graph and X tags, then React's `renderToReadableStream` output of the same `App`. The page's data comes from the same `Operations` the API uses, bounded at 1.5 to 2.5 s so a slow read degrades to client loading: the swarm list, or a swarm's detail and its room. It is followed by `window.__SWARMS_BOOT__` with that data, the config, the server time, the visitor's time zone (cookie `swarms_tz`), whether the device is a phone, and the remembered wallet (cookie `swarms_face`, which `wallet.ts` mirrors from localStorage). The server uses `#ssr` (`src/web/server.tsx`, aliased in `vite.config.ts`), and its components read the request through `boot.ts`: `here()` for the URL, `seeded()` for data (a failure is seeded as `!key`), and the server snapshots of `useMedia`, `useWallet` and `usePath`. `main.tsx` loads the route's module and hydrates (`pages.tsx` keeps the code split while letting the server and hydration render a page without Suspense), so the first paint is the final layout, and polls seeded on the server wait one interval before refetching. Times are formatted in the visitor's zone on both sides. A missing swarm answers 404 with its page. Fixture and storyboard URLs (`?fixture`, `?scene`) stay client-rendered. ## Rooms

- Every swarm has a room where its backers talk (the user's request of 2026-11-01). Anyone reads it; a backer posts. A backer is an address with a counted contribution, or a hand issued while it was signed in (`hands.contributor`, migration 0008; hands issued signed out, over MCP or before 0008 have no owner and make nobody a member). `Store.members` lists them with `backed` (what they put in), `steered` (what of it is behind a note, from a note on the money or from the room) and `available`, the difference.
- Sign-in is accounts' `Handler.auth` (SIWE, the accounts `examples/authentication` pattern) at `/v1/auth`, `/v1/auth/challenge` and `/v1/auth/logout`, with `cookie: false`, so every session is a bearer token, 30 days, and `origin` pinned to `SWARMS_URL`. Its store is the D1 table `sessions` (`Sessions.store`: `take` is `delete … returning`, so a challenge nonce is used once, and expired rows go on every write) rather than the example's Durable Object. The page signs in with one Tempo Wallet prompt: `wallet_connect` with `capabilities.auth = { url: config.auth, returnToken: true }`, keeps `{ address, token }` in localStorage and sends `Authorization: Bearer` on every `/api` request. Funding does not sign anyone in, so sending money never depends on the session handshake. A room that answers `me: null` to a token the page holds signs the page out. A Tempo access key signs in as its wallet too (2026-11-06, the user's request to run everything headless with the wallet's access keys): accounts calls viem's `verifyMessage`, whose Tempo chain refuses a keychain envelope unless `mode: 'allowAccessKey'`, so `Sessions.auth` hands it a client whose chain's `verifyHash` sets that mode, which recovers the access key and checks on the AccountKeychain that it is authorized for the wallet, not expired and not revoked. Before, the admin access key's signature answered 401 `signature does not match address`. Locally with viem, the admin key's signature verified for its wallet, and a key the wallet never authorized and a plain EOA claiming the wallet did not.
- A backer's name in the room is their username. Since 2026-11-05 ("require people to set a username instead of the automatic guest usernames") posting, steering and side questions need one: `Operations.say` and `Operations.btw` answer 403 `username_required` to a signed-in account without a name, and the room's gate and the transcript's composer ask for one (`Username.tsx`) before they show a composer. Someone without a username, a backer who funded without signing in, shows as a short address (`Mention.short`, `0x73dd…c0c0`, written without `@` by `Mention.at`) in the room, the transcript, the contributors and the team roster, and is not offered in @-completion. Before, such a backer got a made name, `Mention.handle(address)`: one of 64 words picked by the address's first four bytes and its last four hex digits (`@quark-1a2b`), which still resolves as a mention in old messages. A signed-in account sets its username with `POST /api/me` or `/v1/me` `{ name }` (the user's request of 2026-11-02; `null` or `""` clears it) and reads it with `GET`, and the header's wallet button shows `@name`. Usernames live in D1 `names` (migration 0009), keyed by lower-case address, unique, stored in lower case, 3 to 24 letters, digits, `-` and `_`, starting with a letter and ending with a letter or digit (`Mention.invalid`). A name shaped like a made one (`word-1a2b`) is refused, so nobody can pass for another backer's made name, and so are `swarm`, `lead`, `all`, `everyone`, `here`, `admin`, `system`, `swarms` and `you`. A taken name is 409 `conflict`; a released name is free at once. Mentions resolve against both names, the username and the made one, when a message is posted, and are stored as addresses; a message's text keeps the name it was written with, so a mention of a username that was later changed no longer highlights. The page highlights messages that mention the reader.
- `@swarm` steers. A message with it must carry `steer`, an amount of the author's `available` backing that goes behind the rest of the message (`Mention.idea`, 3 to 280 characters) as a note: a row in D1 `steers`, inserted only when the author's available backing covers it, in one statement, so two concurrent steers cannot spend the same backing (409 `insufficient_balance`). `Store.notes` adds `steers` to the other notes, so a room steer weighs like a note on money, merges with the same note's money (`noteId` normalizes case and spaces), counts its author as a backer of the note, is indexed for search and is in every continuation prompt. ## Contributor hands

- Anyone can lend a swarm their own machine as a nanocode hand. `POST /v1/swarms/:id/hands` (also `/api`, and the MCP tool `swarm_hand`) takes an optional `label` and answers the hand's `name`, `token` and `url`, plus both ways to attach:
  - `cli`: `nc hand '<url>' --token <token>` (nanocode 0.6.7), and `command`, the gateway's line that installs nanocode first.
  - `library`: a Node module that runs nanocode-ts's `Hand.connect` over its in-memory shell (`Connect.library`, release build-20f97e0, installed with `npm`).
  - `GET /v1/swarms/:id/hands` lists the issued hands and which are connected. The swarm page's "Connect your machine" box (`Connect.tsx`) issues one and shows both forms.
- A hand is an account hand of the operator key in the swarm's app (`POST /v1/hands?name=` with `Gateway-App: swarm-<id>`; see the gateway's AGENTS.md on account hands), so the agent and its subagents can use it in every turn, whichever contribution pays.
- Hands issued before `upgrade`, under a swarm's old pool key, stop attaching, and so do all hands when the operator key changes; contributors issue new ones.
- Hand pricing belongs to the gateway and the hand SDK: an owner prices their own hand (`nc hand <url> --token <t> --pricing prices.json` with `{"payee","describe","rules":[{"paths","ops","usd"}]}`, or nanocode-ts `Hand.connect(…, { pricing: { payee, describe, price(operation) } })`), the gateway's hub charges the agent that made each priced call before it releases the reply (operation `hand.use` on `/mcp`, so this app's payer pays it like any MCP call, at the price as `amount`), and the gateway pays the payee in USDC.e. So Swarms keeps no prices, meters nothing and sends no payouts (the user's decision of 2026-10-31, after a first version that metered and paid hands from the swarm's wallet). It reads `GET /v1/hands`: `requests` (gateway 8c471aa: the operations the hub dispatched, the hand's environment probe included, never counted again on a replay) and, from gateway `feat/paid-hands` (agent 14's branch, not deployed on 2026-10-31), `pricing` (`payee`, `describe`), `charges` (`count`, `usd`, billed to this account's agents), `earned`, `paid` and `cap`. `Hands.terms` turns them into the price summary, charges and earnings that the Connect box, the hands API and the agent's prompt show (`test/hands.test.ts`). At each turn's start `cap` sets every connected hand's cap to a fifth of what is left to spend with `POST /v1/hands/<name>/cap` `{ usd }`, which starts a new window each time, and a hand that joins mid-turn gets the same cap; it sends a cap only for hands whose listing has a `cap` field, so nothing reaches a gateway without caps.
- Lent hands are paid over MPP channels to their owners (2026-10-31, with gateway `feat/mpp-hand-billing`, not deployed that day): for a hand charge the gateway's payer request carries the owner's OUSD session challenge first, with `recipient` (the owner's address) and `hand`, and each channel snapshot names its `payee`. `Swarm.charge` then tries the swarm's wallet on a channel of its own to that owner first (source `hand:<payee>`, its mppx store `mppx:hand:<payee>:`, opened with 0.05 or the price, whichever is more, and topped up by 0.05, smaller than the gateway channel's 0.1 because it can pay only that owner), and only when the wallet cannot (no OUSD left, a USDC.e owner, a refused credential) falls back to the usual sources paying the gateway's challenge, which the gateway turns into its payout to the owner; a MACH pledge always falls back, because MACH cannot reach an owner. `Payer.offer` takes the recipient and now hands mppx a 402 with only the chosen challenge: before, a wallet paying the gateway's OUSD challenge on a hand charge would have signed the owner's OUSD challenge, the first in the list. The owner channels count in `pool_spent`, not in what the swarm may spend, since their deposits pay only their owner. At done `settle` closes them with `requestClose` from the wallet (no cooperative close: the gateway's `kv/get` route takes only its own channels), which the gateway's close supervision answers, and the refund waits for every such channel's deposit to reach 0 (`closing:hand:<payee>`). `Hands.terms` adds `channels` (what the owner was paid over channels and how much settled) and the price's currency, which the Connect box and `Lent` in the OpenAPI document show.
