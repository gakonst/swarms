# Swarms

A community-funded science project on the Tempo gateway (https://gateway.tempo-dev.workers.dev): anyone starts a research swarm with a question and evidence requirements, funds it with a one-off transfer, a daily budget or a pledge, and can contribute to an existing swarm or lend a machine. Swarm World makes the research visible. It uses only the gateway's public HTTP API, as any outside developer would, so it also tests that API.

## Research experience

- The home page is the world: a short introduction and the funded-swarm landscape, with no duplicate directory, long explainers or setup code. `World.tsx` polls only the listing every five seconds. Outposts show status and round; the selected mission has a short field note, funding and a link into the expedition. Advanced explanation stays in disclosures. The landscape is schematic; area labels are inferred from titles and briefs.
- `New.tsx` is a three-step quest flow: Choose, Equip, Launch. Starter cards preserve the full scientific briefs in `research.ts`; a custom question gets an editable evidence brief. No swarm is created until the final launch action. Back navigation preserves the budget and brief. Wallet permissions remain available before launch, and funding still requires Tempo Wallet approval. Token choices and priority notes are optional setup details.
- `Mission.tsx` makes round history and the research party the primary swarm view. Clicking a researcher reveals its observed state, current action, completed tool actions, assignment and result. Selecting a past round shows its recorded party. Findings, funding, machine lists, community notes and raw logs remain accessible. Mobile selection scrolls to the selected researcher; motion respects reduced-motion preferences.
- Subagent progress was previously dropped by `Swarm.digest`. The runtime serializes it as `source: "subagent"` with `root_session_id` and `update`, whose types are `added`, `event`, `status`, `completion` and `message`. Evidence: `gakonst/nanocode` commit `f6dfa4ec82fdbff4a0b5587dc14d8b2ad386bb05`, `crates/runtime/agent/src/session_events.rs`, and `crates/runtime/subagents/src/model.rs` and `tools.rs`. `Gateway.Event` now preserves that envelope; `shared/Research.ts` reduces named task and lifecycle updates.
- Each Durable Object creates a `researchers` SQLite table, keyed by runtime-scoped researcher identity and round. Replayed gateway sequences do not increment counters. A confirmed tool result increments actions; a completed model run does not complete a research assignment. Only explicit runtime task status/completion does that. Late completions retain their original round; a new observed `run.started` can carry the same researcher into a new round while preserving the earlier snapshot. Reasoning and token deltas are ignored. Detail and public overview responses expose additive `researchers` snapshots, documented in OpenAPI.
- Old feed entries do not contain lost subagent metadata, so there is no invented historical backfill. Existing runs show aggregate counts until new runtime updates arrive. Deployment of the Worker is needed for live per-researcher tracking; the clearly labeled fixture world supplies demo snapshots for UI inspection. A completed agent task or round is reported execution progress, not independently verified science. No fake research percentage, XP, token reward or investment return is shown.
- Checked locally on 2026-10-30: `pnpm check`, `pnpm build`, and `node --test test/research.test.ts` (seven lifecycle/brief tests). Browser fixture checks covered world-to-mission navigation, selecting active and reported subagents, round history, the three setup steps and preserving a budget on back navigation. A 375-pixel iframe checked mobile quest choices and researcher selection. Wallet payments were not exercised. Vite permits the exact `terminal.local` preview host, with no wildcard allowance.

## How it works

- A pledge is a gateway API key on the contributor's wallet. `POST /api/swarms/:id/pledges` asks the gateway for a key (`POST /api/keys/request` with `deposit` = the pledge, `topUp: 0`, `limit` = the pledge rounded up to whole MACH, at least 1, which is the gateway's minimum, and 7 days). The page has Tempo Wallet approve it (`wallet_connect` with `authorizeAccessKey`), and `POST /api/swarms/:id/pledges/:pledge` completes it (`POST /api/keys/complete` with the `keyAuthorization`, or a signed `transaction` carrying it, as scripts send). The token is stored AES-GCM-sealed with a key derived from `SWARMS_SECRET`. The key's channel opens with exactly the pledge and never tops up, so the swarm can spend at most the pledge, and the money stays in the contributor's wallet until the channel opens. Completing checks the wallet's balance of the pledge's token (`GET /api/keys/me`) and refuses a pledge it cannot cover.
- A pledge is in MACH, OUSD, USDC.e or pathUSD (`token`, MACH by default; `pledges.token`, migration 0005), and its gateway key is in that token (`POST /api/keys/request` `token`). The gateway's sessions take MACH and OUSD, so a USDC.e or pathUSD key settles in OUSD: its authorization carries its own token (the pledge rounded up, plus 1%) and an OUSD limit, and its channel opens through mppx's `autoSwap`, which spends OUSD the wallet already holds and swaps the rest from the key's token on the stablecoin DEX inside the open. On 2026-10-30 a 0.25 pathUSD pledge from the test wallet, approved by its admin key, ran a round for $0.003748 on the deployed gateway; the wallet held OUSD, so its 0.25 OUSD went into the channel (0xdf1df182…) without a swap. Amounts are labeled with their token wherever one token is meant (each pledge, transfer and budget) and in dollars wherever several add up (totals, note weights, round spend), at par.
- MACH cannot be pooled. MACH's TIP-403 policy (compound policy 583: any sender, recipients from whitelist 582, any mint recipient) lets MACH reach only whitelisted merchants such as the gateway's recipient and the escrow. A `transferWithMemo` from a funded wallet to a fresh swarm address reverted with `PolicyForbids`, and the MACH swapper's `swapTo` reverted for any recipient but a merchant (checked on Tempo mainnet on 2026-10-30). USDC.e (policy 1), pathUSD and OUSD (policy 2) can reach a fresh address, so pooled money is in those, and MACH backs a swarm only as a pledge.
- Every swarm has its own wallet: a secp256k1 key generated when the swarm is created (or on first read for older rows), AES-GCM-sealed with `SWARMS_SECRET` in `swarms.sealed_wallet`, its address in `swarms.wallet` (migration 0003). Money pooled there pays for rounds through the swarm's own gateway API key, so the swarm custodies it: what the pool did not spend goes back when the swarm is done (below).
- One-off contributions: a `transferWithMemo` of USDC.e, pathUSD or OUSD from any wallet to the swarm's address, then `POST /api/swarms/:id/contributions` with its `hash` and an optional `note`. The Worker reads the receipt and counts the TIP-20 `Transfer`s to the swarm whose `from` is the transaction's sender (so a swap's or a channel close's transfers into the wallet are not contributions); the contributor is that sender. A note counts only when a `TransferWithMemo` to the swarm carries `keccak256("note:<swarm>:<note>")` (`Memo.memo`; without a note the page sends `keccak256("swarm:<swarm>")`), so nobody can attach a note to someone else's transfer; a hash counted without a note can get its note later, and each hash counts once (409 after).
- Daily budgets ("X a day"): `POST /api/swarms/:id/budgets` with `token` (usdce, pathusd or ousd), `amount` per day (at least `minPledge`) and an optional `note` generates a secp256k1 access key for that contributor, kept sealed in `budgets`, and answers its `authorizeAccessKey`: a periodic limit of `amount` with `period` 86,400 s, the token's `transferWithMemo` scoped to `recipients: [swarm wallet]`, 30 days. Tempo Wallet approves it with `wallet_connect` (nanocode-ts machines' pattern, with `keyType: secp256k1`), and `POST /api/swarms/:id/budgets/:budget` verifies the signed authorization against the request (key, chain, expiry, token, period, limit at most the request, scopes) and stores it; the first pull carries it on Tempo. A script whose approver is an admin access key sends instead a signed transaction carrying the authorization, which the Worker broadcasts (the approver pays its fee): on 2026-10-30 a pull whose own transaction carried an admin-signed authorization was refused at `prepareTransactionRequest` with `An internal error was received`. A pull pays its fee in the budget's token from the contributor, inside the same limit: on 2026-10-30 a 0.01 pathUSD pull used 304,090 gas and lowered the remaining limit from 0.03 to 0.019817 (0.000183 of fee), a transfer to any other address answered `CallNotAllowed`, and one past the remaining limit `SpendingLimitExceeded`. So no swarm money sponsors a contributor's transfer, and the first pull works with an empty pool. A key with no OUSD limit could not pay its fee in OUSD, while OUSD works as a fee token for the swarm's own transactions (a 33,530-gas OUSD transfer paid in OUSD).
- Pulls: before a round and whenever the pool holds less than `reserve` + `perWorker` during one, the swarm fills its pool up to `stock` (the reserve plus three explorers' shares, 0.42) from budgets. It reads each active budget's `getRemainingLimit` (remaining and `periodEnd`), `getMetadata` (revoked) and the wallet's balance, takes the least recently pulled budgets, one per 0.03 still needed, and splits the need evenly among them, each capped at what it can give after its fee. Each pull is a `transferWithMemo` (`keccak256("budget:<swarm>:<budget>")`) signed by the budget's key, recorded as a `pull` contribution. A budget used up for its period waits until `periodEnd`, one whose wallet holds too little waits 15 minutes, and a revoked or expired one stops; the swarm page shows each one's next pull time. With every budget waiting and no other money, the swarm pauses until the earliest next pull.
- Spending the pool: the swarm swaps its USDC.e and pathUSD into OUSD on the stablecoin DEX (`swapExactAmountIn` with `minAmountOut` 0.5% under `getSellQuote`, paying the swap's fee in the input token and leaving 0.002 of it for fees), then tops its own OUSD gateway key's channel up with all its OUSD (`POST /api/keys/topup`). The key (limit 100 OUSD, a 0.5 USDC.e `search` limit, 30 days, `token: ousd`) is requested and approved by the swarm itself: its root key signs the `authorizeAccessKey`, and `POST /api/keys/complete` takes the `keyAuthorization`. Measured on 2026-10-30: 0.1 pathUSD quoted 0.1 OUSD (fee 0.000052 to 0.000351 per swap, 584,841 gas) and 0.112794 USDC.e quoted 0.112782 OUSD. A round runs on the pool whenever it holds at least `reserve`, so the pool's lead agent is one agent for the swarm's whole life; pledges pay when the pool is empty, each on its own key and agent, and an agent coming back after rounds it missed is sent their reports.
- Search: the gateway's agents pay web search providers, which take only USDC.e, from the key's own wallet when the key has a USDC.e limit, so the pool key asks for `search: 0.5` (the gateway's default is 0, because a USDC.e `transferWithMemo` scope reaches any address) and the swarm leaves 0.1 USDC.e of what it pools unswapped for it. On 2026-10-30 a 0.3 USDC.e transfer was swapped down to 0.101794 USDC.e, the pool key's install carried limits of 100 OUSD and 0.5 USDC.e (0x22cb152f…), and when the swarm was done the kept USDC.e was swapped and returned with the rest (0.29044 OUSD, 0xfe8824e2…).
- Weights: a note's weight is everything behind it, pledged, sent or pulled; stablecoins count at par (MACH, OUSD, USDC.e and pathUSD are USD tokens, and the DEX quoted them within 0.02% of each other above). Explorers follow what the round can spend: the pool's channel plus what is still to be swapped and deposited, or the pledge's channel.
- Done: pledges are revoked as before, budgets end (their keys stay valid on chain until the contributor revokes them in Tempo Wallet or they expire; the swarm never pulls again), the swarm's own key is revoked, which closes its channel into the swarm's wallet, and once that OUSD has arrived (or after 20 minutes) the swarm sends what it holds, less 0.004 for fees, back to its transfer and budget contributors in proportion to what each put in.
- Checked on 2026-10-30 locally (`SWARMS_GATEWAY=http://localhost:5821` against the gateway's feat/ousd-keys under `vp dev` with the AI binding): a 0.03 pathUSD transfer with a note was counted once (a second post answered 409) and swapped to OUSD; an admin-approved 0.1 pathUSD-a-day budget was pulled for 0.099875 (fee 0.000041), then showed `waiting` until its `periodEnd` with 0.000084 left; the swarm authorized its own OUSD key, moved 0.119424 OUSD into its channel, and its one lead agent ran two rounds for $0.006450; when it was done it returned 0.107974 OUSD to the contributor. A second swarm ran four rounds on its pool ($0.011485) with a 0.15 pathUSD budget, a 0.02 OUSD transfer and a 0.1 MACH pledge, whose notes weighed 0.249512 (pledge plus pull, 92.6%) and 0.02 (7.4%), and returned 0.151927 OUSD. A third pulled 0.044785 pathUSD from a wallet holding 0.05, marked that budget unfunded, pulled 0.114794 USDC.e from a second contributor's budget (each first pull carried its root-signed authorization; this one's fee, with the key's install, was 0.002151 USDC.e), noticed that budget's revocation on Tempo 2 s after it, and returned 0.107054 and 0.041765 OUSD to the two contributors (71.9% and 28.1%, their shares).
- `Swarm` (one Durable Object per swarm, binding `SWARMS`) runs it on alarms. A round is one turn of a Codex lead agent (`POST /v1/agents`, then `POST /v1/agents/:id/turns` with `steer: false`), paid from one pledge. The swarm keeps the same pledge, and so the same agent, while it has at least `reserve` (0.06 MACH) left, then uses the active pledge with the most left. A new pledge means a new key and a new agent, primed with the last three round reports. While a round runs, the object pages `GET /v1/agents/:id/events?after=` every 2 s into its feed, and every 10 s it reads the turn, the key's `usage.channel.spent` and `GET /v1/hands` (the machines the agent attached with `compute_create({ attach })`).
- More money means more parallelism: a round runs the lead alone below `reserve` + `perWorker` (0.12 + 0.1 MACH) left on its pledge, and gets one `spawn_agent` explorer more per `perWorker`, up to 3 beside the lead. A pledge is at least 0.25 MACH. The gateway reserves a model call's full output limit until the call ends, about 0.04 MACH on DeepSeek V4.1 Flash, plus a machine's whole lease. On the deployed app on 2026-10-30, a 0.1 MACH pledge whose lead started a machine and an explorer at once got `The key's channel has 0.029621 MACH left and automatic top-ups are off` on its next model call: the round failed with 0.0506 MACH reserved and under 0.01 spent. With the lead alone on a 0.1 MACH pledge, the fifth model call of a round still got `0.02901 MACH left`: the gateway credits a call's unused reservation in `waitUntil` after its response, so the next call's reservation can overlap the last one's. The reserve and the per-explorer share therefore cover two calls each. After a failed round the swarm waits 15 s for refunds before it rereads the pledge, a pledge is released only once its settled spend leaves less than `reserve`, and every round's end and every release terminates sandboxes the agent left running (`POST /v1/compute/list`, then `compute/terminate`).
- Contributors steer with money. A pledge may carry a note; pledges with the same note (normalized) back it together, and its weight is the MACH behind it. A pledge with a note that arrives during a round steers that round (`steer: true`), with its weight and its share of everything pledged. Every round's prompt lists the notes by weight.
- A pledge is checked against its key's live channel (`GET /api/keys/me`) before every round, not only against the spend recorded in D1, and a round that fails with a 402 releases the pledge that paid it, so the swarm moves on to its next active pledge. On 2026-10-30 swarm 06cf5d7c8f92's 5 MACH pledge channel was closed mid-round by an outside `requestClose` (0x870aac79…, one transaction closing 24 of the test wallet's channels): D1 still recorded 4.398 MACH left, so every later round picked the dead pledge, got `The key's channel has -0.602134 MACH left`, and after three failures the swarm paused with a 0.25 MACH pledge unused. `Memo.units` also read `-0.602134` as positive. The paused banner shows the swarm's real reason (`Detail.reason`), and a swarm paused before this check ran is retried once when it is next viewed.
- A round ends with `STATUS: done` or `STATUS: continue: …`. Nothing limits a round's length or the number of rounds: a swarm runs until its lead reports the goal met or its pledges run out (the user asked on 2026-10-30 to drop the 5-minute round target, the 12-round cap and the 30-minute turn cancel). Only three failed rounds in a row pause it. On done, every active pledge's key is revoked (`POST /api/keys/revoke`), which closes its channel and returns the unspent deposit to the contributor within about a minute. A used-up pledge is revoked the same way. A key the gateway retires (401) ends its pledge.
- Checked on 2026-10-30 locally (`vite` with the Cloudflare plugin, against the deployed gateway, with pledges approved by a test wallet's access key): a 0.1 MACH pledge ran one round in 75 s that attached a Modal machine, benchmarked zlib, bz2 and lzma and terminated the machine, then ended the swarm, spending 0.0104 MACH. A 0.3 MACH swarm was steered 30 s into its round by a second pledge with a note ("Also report peak memory (RSS) for each parser"). The agent added the measurement, and the round cost 0.0327 MACH.
- The page funds a swarm three ways in one box (`Contribute.tsx`): send once (Tempo Wallet's `eth_sendTransactionSync` with a `transferWithMemo` of USDC.e, pathUSD or OUSD to the swarm's wallet, whose memo is `Memo.memo(swarm, note)`, then `POST …/contributions` with the hash), a daily budget (`POST …/budgets`, then `wallet_connect` with the returned `authorizeAccessKey`, then `POST …/budgets/:budget` with the `keyAuthorization`) and a pledge in any token, MACH preselected. The swarm's wallet links to the explorer, and the swarm page lists budgets (amount a day, pulled, left today, status and next pull), transfers and pulls, and pledges. The box prefills from the link `swarm_budget` and the other MCP tools hand out: `?fund=transfer|budget|pledge` picks the mode, and `token` (`usdce`, `pathusd`, `ousd`, or `mach` for a pledge), `amount` and `note` fill the fields.

## API and MCP

- Every operation lives in `Operations` as a function of `(env, input)` returning a `Problem.Result`. The web app's `/api` routes, the public `/v1` routes (`Rest`) and the MCP tools (`Mcp`) are thin adapters over these functions, so validation, errors and side effects match on every surface. That includes the transfers and daily budgets above (`contribute`, `budget`, `allow`), which `/v1` serves under `/v1/swarms/:id/contributions` and `/v1/swarms/:id/budgets`, and the wallet a swarm from before 0003 gets on its first read. Each operation parses its own input with Zod, and the schemas have no transforms: the MCP SDK validates a tool's arguments with the same schema and passes on the parsed value, so a transforming schema (the pledge amount to atomic units) failed when the operation parsed that value again.
- `/v1` is the public REST API, described by `/openapi.json` (OpenAPI 3.1, request bodies from `z.toJSONSchema`). `/v1/*`, `/openapi.json` and `/mcp` answer CORS for any origin, and the web app's `/api` stays same-origin. Errors are `application/problem+json` with a stable `code` (`Problem.codes`). `run_worker_first` lists these paths, because the assets' single-page fallback would otherwise answer them with `index.html`.
- Vite's dev server answers `OPTIONS` itself, without `Access-Control-Allow-Origin`, so preflights are checked against the build (`wrangler dev -c dist/swarms/wrangler.json`). There on 2026-10-30, `OPTIONS /v1/swarms` and `OPTIONS /mcp` answered 204 with `*`, and `/mcp` exposed `mcp-protocol-version` and `mcp-session-id`.
- `POST /mcp` is a stateless streamable-HTTP MCP server (`WebStandardStreamableHTTPServerTransport` with `enableJsonResponse`, one server per request). `GET` and `DELETE` answer 405, because there are no sessions and no server-sent notifications. It has 13 tools: `swarms_list`, `swarm_get`, `swarm_answer`, `swarm_rounds`, `swarm_feed`, `swarms_search`, `swarm_create`, `swarm_pledge`, `swarm_contribute`, `swarm_budget`, `swarm_hand`, `swarm_pledge_status` and `swarm_wait`. Its instructions explain swarms, rounds, the three ways money comes in, notes and lent machines.
  - Funding over MCP: `swarm_pledge` uses the device flow below.
  - `swarm_contribute` without `hash` prepares a one-off transfer (`Operations.transfer`). It answers:
    - the swarm's wallet, which a swarm from before 0003 gets now;
    - the token's address and the memo, `Memo.memo`, the same one the page signs;
    - with `amount`, the `transferWithMemo` call data;
    - a link `/s/<id>?fund=transfer&token=&amount=&note=`, where the page sends it with Tempo Wallet and counts it.
    With `hash` it counts a transfer already sent (`Operations.contribute`). The server never sends money: the user's wallet does.
  - `swarm_budget` validates a daily budget and answers `/s/<id>?fund=budget&token=&amount=&note=` with the swarm's wallet and the key's limits. A budget key is generated by the swarm and approved with Tempo Wallet's `wallet_connect`. The gateway's device-code registration (`register` in its `Keys.ts`) sends only its own key requests, so this app has no device flow for budget keys, and the page approves them.
  - The contribution box reads those parameters (`asked` in `Contribute.tsx`). Checked on 2026-10-30:
    - The budget link opened the Daily budget tab with USDC.e, 1.000000 and the note.
    - The transfer link opened Send once with pathUSD, 0.500000 and the note.
    - The prepared call for 0.5 pathUSD decoded to `transferWithMemo(swarm wallet, 500000, keccak256("note:<id>:Add HTTP/2"))`. An `eth_call` of it from the test wallet succeeded, and nothing was sent. The server runs no model: the client's own model answers questions about the data by calling the tools, so reading costs nothing. An argument the SDK rejects comes back as an `isError` result with `MCP error -32602`. An operation's failure comes back as an `isError` result holding its problem JSON.
- Clients without a browser wallet pledge through Tempo Wallet's device flow. `device: true` on `POST /v1/swarms/:id/pledges` passes `device: true` to the gateway's `/api/keys/request` and stores the user code, the link, the interval and the expiry in `pledge_devices` (migration 0004). The caller polls `GET /v1/swarms/:id/pledges/:pledge?wait=` (or `POST` with `{}`), which calls `/api/keys/complete` with only the request id.
  - Outcomes: 200 (or 202 for the `POST`) while the pledge is pending, 201 once it is active, 403 `access_denied` when the request was declined, and 410 `expired` past the expiry. A declined or expired pledge is forgotten, so later polls get 404.
  - `swarm_pledge` always uses the device flow, because an MCP client holds no wallet, and answers with the link to open.
  - The gateway answers 404 for a request it no longer holds. That also happens when another poller completed the same pledge a moment earlier, so on a 404 the poll reads the pledge again and answers it active when it is.
  - Checked on 2026-10-30, locally:
    - A device pledge polled after its expiry answered 410 `expired`, and then 404.
    - A refusal, run against a mock gateway (a Node server whose `/api/keys/complete` answered pending and then 403), answered 403 `access_denied` over REST and over `swarm_pledge_status`.
    - A device pledge was never approved with a real wallet. Its success path is the same `activate` that two real browser-flow pledges went through: the web app's `/api` flow and `/v1`'s `keyAuthorization` flow.
- `swarm_wait` and `GET /v1/swarms/:id/wait` wait at most 55 s per call (`maxWait`), as does a pledge poll's `wait`. The MCP SDK client's default request timeout is 60 s (`DEFAULT_REQUEST_TIMEOUT_MSEC` in `@modelcontextprotocol/sdk` 1.32.2). A caller that wants to keep waiting calls again. This bounds only the wait: the swarm itself has no time limit.
- Search is a D1 FTS5 table, `search` (porter on `unicode61 remove_diacritics 2`, migration 0004). It indexes swarm titles and goals, notes and round reports, and ranks by `bm25` with titles weighted 2 and bodies 1. A query keeps its words minus stopwords, each quoted and joined with `OR`, so a query's punctuation can never reach FTS5 syntax. Like the list, search hides swarms that nothing funds: no approved pledge, no transfer or pull, and no active budget.
  - When rows are indexed: a swarm when it is created, a note when its pledge activates, its transfer is counted, its budget is approved or a budget with a note is pulled, and a report when its round ends (`Swarm` calls `Search.report`).
  - `Search.sync` fills in reports that are missing or changed. Reads of a swarm call it, and so does every search: an unscoped search checks the 5 most recent swarms with more rounds than indexed reports (`lagging`), which also covers rounds from before 0004.
  - Feed entries stay in the Durable Object. A search scoped to one swarm also scans that swarm's feed there (`Swarm.search`).
  - Checked on 2026-10-30 on a scratch D1 database on the Tempo account (`swarms-fts5-check`): created, migrated with 0001, 0002 and 0004, queried with `Search.query`'s exact SQL, then deleted. Porter stemming, `bm25` and `snippet` worked; production D1 refused read-only pragmas, so this was the check.
- D1 export does not support databases with virtual tables (Cloudflare's import and export docs: drop them, export, recreate them). Before `wrangler d1 export`, drop `search`. Afterwards, rebuild it from `swarms`, the notes of `pledges`, `contributions` and `budgets`, and `reports`, which holds every indexed report.
- `/docs` (`Docs.tsx`) documents the MCP server, the REST routes, the pledge flows, transfers and budgets, contributor hands, and the error codes. The home page's "Use it from code" section links to it.
- Checked end to end on 2026-10-30, locally:
  - `@modelcontextprotocol/sdk`'s client called every tool.
  - A script that answers questions through `swarms_search` and then `swarm_rounds` answered "Which codec should I use for log archives?" with bz2, from a round report, and "Which Python HTTP client used the least peak RSS memory?" with urllib3.
  - The two local swarms behind those answers spent 0.017463 and 0.027562 MACH.

## Contributor hands

- Anyone can lend a swarm their own machine as a nanocode hand. `POST /v1/swarms/:id/hands` (also `/api`, and the MCP tool `swarm_hand`) takes an optional `label` and answers the hand's `name`, `token` and `url`, plus both ways to attach:
  - `cli`: `nc hand '<url>' --token <token>` (nanocode 0.6.7), and `command`, the gateway's line that installs nanocode first.
  - `library`: a Node module that runs nanocode-ts's `Hand.connect` over its in-memory shell (`Connect.library`, release build-20f97e0, installed with `npm`).
  - `GET /v1/swarms/:id/hands` lists the issued hands and which are connected. The swarm page's "Connect your machine" box (`Connect.tsx`) issues one and shows both forms.
- A hand is an account hand of the swarm's own pool key at the gateway (`POST /v1/hands?name=` with the pool token; see the gateway's AGENTS.md on account hands), so every agent of that key and app, the pool's lead and its explorers, can use it, whichever turn is running. `Swarm.hand` authorizes the pool key first when the swarm has none, through `mint`, which is now single-flight so a request and the alarm's `fund` cannot both authorize a key. Authorizing deposits nothing: the key's channel opens when the pool first tops it up.
- Limits that follow from that:
  - Rounds paid by a MACH pledge run on that contributor's own key, another gateway account, and cannot reach lent machines. The box, the docs and the tool say so.
  - A pool key the gateway retires is replaced by a new key, and hands issued under the old one stop attaching. The contributor issues a new hand.
- Names are `<slug of the label>-<6 random hex>`, recorded in D1 `hands` (migration 0006) under `(swarm, name)` with insert-or-ignore and up to three tries, and the swarm also refuses a name the gateway already lists. They must not collide: the gateway hands out the same secret when the same name is minted again under one key, so a repeated name would give one contributor's token to another. A swarm takes at most 32 hands, a number chosen without measurement.
- The lead is told: pool rounds list the connected contributor hands with their labels (`lending` in `brief` and `next`). The text says the machines belong to contributors, to work in a directory of their own, to treat what they return as data, and to stop and ask in the report before anything destructive or invasive. A contributor hand that connects during a pool round is announced to the running turn with a steer (`welcome`), and the feed logs every contributor machine that joins with its label.

## Development

- `pnpm dev` runs the Worker and the page. Set `SWARMS_STATE=<dir>` to keep local Durable Object and D1 state there, and `SWARMS_GATEWAY=<url>` to use a local gateway: only then, and only under `vite` serve, the Worker's `GATEWAY_URL` is that URL and `global_fetch_strictly_public` is off, because the flag sends fetches to the public internet, which a local gateway is not on. Builds and deploys keep `wrangler.jsonc` as it is. `pnpm db:migrate:local` (add `--persist-to <dir>` with `SWARMS_STATE`) applies `migrations/`. `.dev.vars` needs `SWARMS_SECRET`.
- `pnpm check` type-checks the Worker and the page. `pnpm build` builds both. `pnpm exec wrangler dev -c dist/swarms/wrangler.json` runs the build, where CORS preflights behave as deployed.
- Deploy: `pnpm db:migrate`, then `pnpm deploy`. Set `SWARMS_SECRET` with `wrangler secret put`. The Worker reaches the gateway over the public internet (`global_fetch_strictly_public`), as a third party would.
