# Swarms

A community-funded science project on the Tempo gateway (https://gateway.tempo-dev.workers.dev): anyone starts a research swarm with a question and evidence requirements, funds it with a one-off transfer, a daily budget or a pledge, and can contribute to an existing swarm or lend a machine. Swarm World makes the research visible. It uses only the gateway's public HTTP API, as any outside developer would, so it also tests that API.

## Research experience

- The home page is the world: a short introduction and the funded-swarm landscape, with no duplicate directory, long explainers or setup code. `World.tsx` polls only the listing every five seconds. Outposts show status and round; the selected mission has a short field note, funding and a link into the expedition. Advanced explanation stays in disclosures. The landscape is schematic; area labels are inferred from titles and briefs.
- `New.tsx` is a three-step quest flow: Choose, Equip, Launch. Starter cards preserve the full scientific briefs in `shared/ResearchBrief.ts`; a custom question gets an editable evidence brief. No swarm is created until the final launch action. Back navigation preserves the budget and brief. Wallet permissions remain available before launch, and funding still requires Tempo Wallet approval. Token choices and priority notes are optional setup details.
- `GET /x` is an X player card for choosing a starter or custom research quest and launching it with a MACH pledge. `GET /x/s/:id` is the matching card for contributing to a live swarm with an optional steering note. Both use the public REST API, request `device: true`, show Tempo Wallet's user code and approval link, and poll the pledge until it activates. The start frame creates the unfunded swarm only when Launch is pressed; no pledge moves money without the wallet approval. The pages publish `twitter:card=player`, Open Graph metadata and an 800×450 preview image, follow xframes' opaque-origin sandbox and no-scroll conventions, and keep the full app as the expedition view. While a round runs, `/x/s/:id` is a live player instead: the frame opens `/v1/swarms/:id/live` and shows who is speaking and what they are thinking, writing or running, with a chip per direction to follow one, and links into the broadcast on that direction; otherwise it shows the latest round's finding.
- The swarm page leads with the broadcast (`Broadcast.tsx`), above the answer while a round runs: a LIVE badge, the round's clock, its activity over time and the rounds to replay; the selected direction's stage (the lead, an explorer or an explorer's own sub-explorer, with a breadcrumb back up); and the directions this round with what each is doing now. The stage shows a direction's assignment, the explorers it sent out, its timeline (thoughts, commands, their output, messages and errors, newest at the bottom and pinned there until the viewer scrolls up), what it is thinking, writing or typing into a tool call right now, and its result, with a JSON result's fields laid out. The selected round and direction are in the URL (`?round=&who=`), so a link opens on one explorer. Choosing a direction or a past round loads its whole timeline with `GET /api/swarms/:id/feed?round=&who=`.
- While a round is on air and the viewer has not picked a direction, the broadcast follows the action: it cuts to whichever direction last streamed or logged something, at most once every 6 s, and picking a direction (or the Follow the action toggle) stops it.
- Every direction is live. The Durable Object stores each subagent's own tool calls, outputs, messages and thoughts in the feed with `who` (its researcher id) and `event` (the gateway event's `seq`), timed by the gateway's `created_at`, and the lead's tool outputs too (kind `output`); before, the feed held only the lead's calls and subagent state changes, so an explorer's work was visible only as its final result. `/live` now forwards every direction: the lead's deltas as before, every subagent's text, thinking and tool-input deltas (`{type: delta, who, channel}`), each feed entry as it happens (`{type: entry}`, `seq` 0) and each researcher snapshot (`{type: researcher}`), reduced by the same `shared/Trail.ts` and `shared/Research.ts` code the object uses, so the page shows an entry at once and the polled copy replaces it by `event` and kind. Subagent events reach the turn's event stream as `source: "subagent"` with `update.type: "event"`, `id`, `parent` and the inner agent event (gakonst/nanocode `crates/runtime/agent/src/session_events.rs`); tool-input deltas are `tool.input.delta` with `call_id`, `tool` and `text`. Old feed entries have no `who`, so earlier rounds replay under the lead.
- A researcher's result is kept up to 20,000 characters: explorers return JSON matching the lead's output contract, the broadcast lays its fields out, and at the earlier 4,000 a long result was cut mid-JSON (swarm f4c1b29ba989's sonic-rs explorer on 2026-11-01) and showed as raw text.
- The fixture world (`?fixture`) plays a scripted live stream (`Fixtures.live`) through the same listener, so the broadcast can be inspected without a running swarm.
- Subagent progress was previously dropped by `Swarm.digest`. The runtime serializes it as `source: "subagent"` with `root_session_id` and `update`, whose types are `added`, `event`, `status`, `completion` and `message`. Evidence: `gakonst/nanocode` commit `f6dfa4ec82fdbff4a0b5587dc14d8b2ad386bb05`, `crates/runtime/agent/src/session_events.rs`, and `crates/runtime/subagents/src/model.rs` and `tools.rs`. `Gateway.Event` now preserves that envelope; `shared/Research.ts` reduces named task and lifecycle updates.
- Each Durable Object creates a `researchers` SQLite table, keyed by runtime-scoped researcher identity and round. Replayed gateway sequences do not increment counters. A confirmed tool result increments actions; a completed model run does not complete a research assignment. Only explicit runtime task status/completion does that. Late completions retain their original round; a new observed `run.started` can carry the same researcher into a new round while preserving the earlier snapshot. Reasoning and token deltas are ignored. Detail and public overview responses expose additive `researchers` snapshots, documented in OpenAPI.
- Old feed entries do not contain lost subagent metadata, so there is no invented historical backfill. Existing runs show aggregate counts until new runtime updates arrive. Deployment of the Worker is needed for live per-researcher tracking; the clearly labeled fixture world supplies demo snapshots for UI inspection. A completed agent task or round is reported execution progress, not independently verified science. No fake research percentage, XP, token reward or investment return is shown.
- Checked locally on 2026-10-31: `pnpm check`, `pnpm build`, and ten tests in `test/research.test.ts` and `test/xframes.test.ts`. Browser fixture checks covered world-to-mission navigation, selecting active and reported subagents, round history, the three setup steps and preserving a budget on back navigation. The X frame was checked at 800×450 and 375 pixels wide for quest selection, MACH presets and launch readiness. Wallet payments and approval were not exercised. Vite permits the exact `terminal.local` preview host, with no wildcard allowance.

## How it works

- One operator API key runs every swarm. `SWARMS_GATEWAY_KEY` is a `sk-tempo-` gateway API key that owns every swarm's lead agent, hands, machines and code repository, each swarm in its own `Gateway-App`, `swarm-<id>`, so swarms never see each other's data. It pays for none of a swarm's work: the lead agent is created with an agent payer (`POST /v1/agents` with `payer: { url: <SWARMS_URL>/api/swarms/<id>/pay, secret }`, tempoxyz/gateway 82d56b6), so the gateway asks this app to pay for every model call, MCP tool call (`compute_*`, `git_*`, `kv_*`) and subagent request the agent makes. A swarm keeps one lead agent for its whole life; `lead` creates it when there is none or the gateway answers 404, and `PATCH /v1/agents/:id` moves the payer when `SWARMS_URL` changes. The operator key pays only the app's own requests: `compute/list` and `compute/terminate` when a round leaves machines running. On 2026-10-31 the operator key was created from the test wallet 0x9759…e122 by its admin key with the gateway checkout's `.scratch/admin-install.mjs` (`REQUEST='{"limit":2,"days":365,"deposit":0.1,"topUp":0.1}'`): access key 0x34e15c9ba6ea1a7061b6077a6520adcc9e298b8d, installed in 0xdd043fd77d3cbaff1df73e37a16c62ee0e698a180211445bf9cedf3d998362dc, expiring 2027-10-31. Agents expire with their key, so a new operator key means new lead agents, each primed with the last three reports. After three local swarms its `/api/keys/me` still showed no channel and its whole 2 MACH limit: it had paid for nothing.
- Every contribution is money or a key the app holds, and contributors fund the same three ways as before:
  - Send once: a `transferWithMemo` of USDC.e, pathUSD or OUSD from any wallet to the swarm's wallet, then `POST /api/swarms/:id/contributions` with its `hash` and an optional `note`. The Worker reads the receipt and counts the TIP-20 `Transfer`s to the swarm whose `from` is the transaction's sender (so a swap's or a channel close's transfers into the wallet are not contributions); the contributor is that sender. A note counts only when a `TransferWithMemo` to the swarm carries `keccak256("note:<swarm>:<note>")` (`Memo.memo`; without a note the page sends `keccak256("swarm:<swarm>")`), so nobody can attach a note to someone else's transfer; a hash counted without a note can get its note later, and each hash counts once (409 after).
  - Daily budget ("X a day"): `POST /api/swarms/:id/budgets` with `token` (usdce, pathusd or ousd), `amount` per day (at least `minPledge`) and an optional `note` generates a secp256k1 access key, kept sealed in `budgets`, and answers its `authorizeAccessKey`: a periodic limit of `amount` with `period` 86,400 s, the token's `transferWithMemo` scoped to `recipients: [swarm wallet]`, 30 days. Tempo Wallet approves it with `wallet_connect` (nanocode-ts machines' pattern, with `keyType: secp256k1`), and `POST /api/swarms/:id/budgets/:budget` verifies the signed authorization against the request (key, chain, expiry, token, period, limit at most the request, scopes) and stores it; the first pull carries it on Tempo. A script whose approver is an admin access key sends instead a signed transaction carrying the authorization, which the Worker broadcasts (the approver pays its fee): on 2026-10-30 a pull whose own transaction carried an admin-signed authorization was refused at `prepareTransactionRequest` with `An internal error was received`.
  - Pledge: `POST /api/swarms/:id/pledges` with `amount`, `token` (MACH by default, or OUSD, USDC.e or pathUSD) and an optional `note` generates a secp256k1 access key the same way, capped at exactly the pledge for 7 days, and stores it in `budgets` with `period` 0: the table holds every key the app holds, and a period of 0 is a one-off cap. A MACH pledge's key may only call the TIP-1034 escrow's `open`, `topUp`, `requestClose` and `withdraw` and pays the gateway itself over its own MACH session channel. A pledge in a stablecoin is a pull key like a budget without a period: the swarm pulls from it into its wallet as rounds need money, and records each pull as a `pledge` contribution, which counts for refunds but not again for `raised` or notes, because the pledge counted its whole amount when it was approved. `POST /api/swarms/:id/pledges/:pledge` approves it with the `keyAuthorization` or a signed transaction (`Keys.approve`, shared with budgets) and refuses a wallet that holds less than the pledge (409 `insufficient_balance`). Pledges made on main before this were gateway API keys, which can pay only for their own agent; the first step of the new code revokes them (`upgrade`), which closes their channels and returns what they did not spend.
- MACH cannot be pooled. MACH's TIP-403 policy (compound policy 583: any sender, recipients from whitelist 582, any mint recipient) lets MACH reach only whitelisted merchants such as the gateway's recipient and the escrow. A `transferWithMemo` from a funded wallet to a fresh swarm address reverted with `PolicyForbids`, and the MACH swapper's `swapTo` reverted for any recipient but a merchant (checked on Tempo mainnet on 2026-10-30). USDC.e (policy 1), pathUSD and OUSD (policy 2) can reach a fresh address. That is why a MACH pledge pays over its own channel while stablecoins are pulled into the swarm's wallet.
- Every swarm has its own wallet: a secp256k1 key generated when the swarm is created (or on first read for older rows), AES-GCM-sealed with `SWARMS_SECRET` in `swarms.sealed_wallet`, its address in `swarms.wallet`. It swaps the USDC.e and pathUSD it receives to OUSD on the stablecoin DEX (`swapExactAmountIn` with `minAmountOut` 0.5% under `getSellQuote`, paying the fee in the input token and leaving 0.002 of it) and pays the gateway from its own OUSD session channel, signed by its root key. Measured on 2026-10-30: 0.1 pathUSD quoted 0.1 OUSD (fee 0.000052 to 0.000351 per swap, 584,841 gas). Before each round, and during one whenever less than `reserve` + `perWorker` is payable or the wallet holds unswapped stablecoins, `fund` fills the wallet up to `stock` (the reserve plus three explorers' shares) from pull keys: it reads each active budget's and stablecoin pledge's `getRemainingLimit` (remaining and `periodEnd`), `getMetadata` (revoked) and the wallet's balance, takes the least recently pulled, one per 0.03 still needed, and splits the need among them. Each pull is a `transferWithMemo` (`keccak256("budget:<swarm>:<key>")`) signed by the key, paying its fee in its own token inside its limit: on 2026-10-30 a 0.01 pathUSD pull used 304,090 gas and 0.000183 of fee, a transfer to any other address answered `CallNotAllowed`, and one past the remaining limit `SpendingLimitExceeded`. A budget used up for its period waits until `periodEnd`, one whose wallet holds too little waits 15 minutes, a used-up pledge is `spent`, and a revoked or expired key stops; the page shows each budget's next pull time.
- The payer is `POST /api/swarms/:id/pay` (`Operations.pay`, then `Swarm.pay`, one request at a time per swarm). It answers only the bearer secret the swarm generated for its agent (64 hex, in the Durable Object, compared in constant time) and only for the swarm's own app, and signs only a `tempo` session challenge to the gateway's recipient 0x40def0Cf3B5d28B6e9a7976BA10591e515AfECFE on chain 4217 for at most $1 (`Chain.cap`, which is what `git_create` costs), or, for a lent hand's charge, an OUSD session challenge to the owner the gateway names in `recipient` (below), so a leaked secret buys gateway requests and hand operations from this swarm's money and nothing else. Its sources are the swarm's wallet (OUSD) and each active MACH key; it tries the wallet first, because its money already left the contributors' wallets and goes back only through refund transfers, then the key that paid last, then the rest by what they can pay now. Each source has its own mppx session client and channel in the object's storage (`mppx:<source>:`, `channel:<source>`). A channel opens with 0.1 or the request's price, whichever is more, bounded by what the source can put in (the wallet's OUSD, or a key's `getRemainingLimit` bounded by the wallet's balance). A voucher is the larger of the gateway's `requiredCumulative`, one past the highest voucher still in flight (signed in the last 10 s and above the accepted one) or else the accepted one, and `spent` plus this source's vouchers not yet accepted plus the price (without a snapshot, one past the last voucher signed); before 2026-10-31 it was always at least one past the last voucher signed, so every voucher the gateway refused or that crossed a refund raised the floor for good and the deposit had to cover it, the arithmetic the gateway's payer contract recommends, so refunded reservations are not paid twice; when the deposit is short the answer carries a `topUp` of at least 0.1 beside the voucher. A source that cannot pay is skipped for this request when its channel still holds a call's reservation (0.04, so it is only busy) or it could pay a smaller request, and rests otherwise: a budget until `periodEnd`, a wallet short of the token for 15 minutes, anything else for 10; a key that is revoked, expired or out of limit ends. A source whose credential the gateway refused on its third attempt rests, and a channel the gateway reports `closing` or refused with 410 is dropped so the next payment opens another. A source whose channel lacks deposit is also busy for 90 s after it last paid, because the shortfall is then mostly other calls' reservations, which the gateway refunds when they end: on 2026-11-01 a web search reserved about 0.18 (0.09 once the SDK sent `max_tool_calls`), two explorers searching at once held all of swarm 48ba542731e3's 0.4, and the next model call was answered `limit_reached`, which rested the wallet for 10 minutes and paused the swarm with 0.37 of it about to come back. When the only sources left are busy the answer is 429 with `retry-after: 2`, which the harness retries; otherwise 402 `limit_reached`, which fails the round's request, and a round that failed with less than `reserve` payable pauses the swarm with the amount and the time a resting source or budget comes back (its alarm). New money wakes it. After a round the object pays one `kv/get` (0.0001) from each source with a channel to read `spent` from its receipt, because the gateway reports `spent` only with each ask, and it includes reservations it refunds after the call.
- A round is one turn of the lead (`steer: false`). It starts when the sources can pay at least `reserve` (0.05) now, together, and gets one explorer per `perWorker` (0.1) beyond that, up to 3. While it runs the object pages `GET /v1/agents/:id/events` every 2 s into its feed and every 10 s reads the turn, the sources and `GET /v1/hands`. A round ends with `STATUS: done` or `STATUS: continue: …`; nothing limits its length or the number of rounds, so a swarm runs until its lead reports the goal met or its money is gone. Three failed rounds in a row pause it, except rounds that failed because the money ran out. Every round's end terminates sandboxes the agent left running.
- Contributors steer with money. A transfer, budget or pledge may carry a note; contributions with the same note (normalized) back it together, and a note's weight is everything behind it, pledged, sent or pulled from a budget, stablecoins at par. A note that arrives during a round steers that round (`steer: true`) with its weight and its share of everything contributed, and every round's prompt lists the notes by weight.
- Done: `done` terminates leftover sandboxes, disconnects the issued hands and ends every budget and pledge (their keys stay valid on chain until the contributor revokes them in Tempo Wallet or they expire; the swarm never spends them again). `settle` then closes every channel: first with a cooperative `close` credential to `kv/get` (for a contributor's key the `CloseAuthorization` is signed with the raw access key, because mppx wraps an access key's signature in a keychain envelope that TIP-1034 refuses), which closes and refunds at once but needs the gateway's session methods to hold a settlement `account` (tempoxyz/gateway 70818b8, not on gateway main on 2026-10-31, where every close credential failed); then with `requestClose` from the channel's signer, its fee paid by the swarm's wallet as Tempo fee payer (the gateway's own `Keys.close` pattern), which the gateway's close supervision answers within about a minute, capturing what was spent and returning the rest to the channel's payer. A MACH key cannot pay its own fee (MACH has no Fee AMM liquidity), so a swarm whose wallet holds no stablecoin cannot close a MACH pledge's channel until the gateway holds the settlement account; it retries for 30 minutes and then logs it. Once the wallet's channel has closed on chain (`getChannelState` deposit 0, or after 20 minutes) the swarm sends what its wallet holds, less 0.004 for fees, back to its transfer, budget and pledge-pull contributors in proportion to what each put in.
- Upgrading a swarm from main (`upgrade`, the first step that finds no payer secret): it revokes the swarm's old OUSD gateway key, whose channel closes into the swarm's wallet, revokes every pledge that was a gateway API key, cancels a round that was running on the old agent, forgets the old agent and pool state, and the next round creates the payer agent, primed with the last three reports. The old key's channel closes into the swarm's wallet within about a minute, so `upgrade` sets `returning` two minutes ahead and `wake` counts it: the first version of this branch paused such a swarm with $0 payable and waited for new money. A swarm that finished on main but had not refunded yet waits for main's `expected` balance as before. Hands issued under the old pool key stop attaching; contributors issue new ones. Checked on 2026-10-31 by running main (0cbafe8) and then this branch on one local state: swarm ebcd9ecbe7bd ran 11 rounds on main's pool key, then this code's first step revoked that key, cancelled round 11 on the old agent and, after a 0.02 pathUSD transfer woke it (before `returning`), created a payer agent that ran rounds 12 to 30 from the swarm's wallet, which now held the old channel's money, until a steering note ended it; its wallet's channel closed (0x47f75e52eb07423357cc4b3c74c9e58b8f427c4334baf68227a032c79ecd3ae3) and 0.150844 OUSD went back (0xe3923483d87f21858abddb9b1c16676a59f794d969c4d78406bf1d54c1056d3f). Swarm 9489bd076e57, done on main, refunded on main before the switch.
- Code: every swarm keeps its code in one public repository on the gateway's `/v1/git` (code.storage over MPP), in its own app and owned by the operator key. The lead creates it itself with `tools.mcp__gateway__git_create({ name, public: true })` when the round prompt says the swarm can afford it, so the swarm's money pays the $1 through the payer and the operator key pays nothing. The prompt offers it once the swarm holds $1.50 (`Store.repoAt`, the larger of what is payable now and what is unspent) and some single source can pay $1.04 (the $1 plus a call's reservation), and before that tells the lead to keep results in the report; the page says the same. Each round's prompt names the repository and how to push: `git_commit` from a cell for text files, or `git_remote` for a clone and push URL from a Modal machine with `apt: ["git"]`. The URL carries a token, so every feed entry, report and live delta is redacted (`https://***@`, and any `eyJ…` JWT becomes `[redacted]`). The app reads the repository without a key through the gateway's public routes (`GET /p/<operator wallet>/swarm-<id>/git[/<name>/log|files|read|diff]`, gateway 5b5c47d): after each round it takes the first public repository of the app (the lead once named one `wc` instead of the name it was given), records the head before the round as the round's `base` and the commits after it as its `commits`, and the round's feed line names them. The page's Code section (`Code.tsx`, loaded lazily) reads the same routes from the browser: a file tree with @pierre/trees, the selected file at the head with @pierre/diffs' `File`, and each round's diff (`diff?ref=<last commit>&base=<base>`, or each commit's own diff for a first round with several) with `PatchDiff`. `/p` answers `Cache-Control: public, max-age=60`, so the page adds a version of the rounds to its URLs.

## API and MCP

- Every operation lives in `Operations` as a function of `(env, input)` returning a `Problem.Result`. The web app's `/api` routes, the public `/v1` routes (`Rest`) and the MCP tools (`Mcp`) are thin adapters over these functions, so validation, errors and side effects match on every surface. That includes the transfers and daily budgets above (`contribute`, `budget`, `allow`), which `/v1` serves under `/v1/swarms/:id/contributions` and `/v1/swarms/:id/budgets`, and the wallet a swarm from before 0003 gets on its first read. Each operation parses its own input with Zod, and the schemas have no transforms: the MCP SDK validates a tool's arguments with the same schema and passes on the parsed value, so a transforming schema (the pledge amount to atomic units) failed when the operation parsed that value again.
- `/v1` is the public REST API, described by `/openapi.json` (OpenAPI 3.1, request bodies from `z.toJSONSchema`). `/v1/*`, `/openapi.json` and `/mcp` answer CORS for any origin, and the web app's `/api` stays same-origin. Errors are `application/problem+json` with a stable `code` (`Problem.codes`). `run_worker_first` lists these paths, because the assets' single-page fallback would otherwise answer them with `index.html`.
- Vite's dev server answers `OPTIONS` itself, without `Access-Control-Allow-Origin`, so preflights are checked against the build (`wrangler dev -c dist/swarms/wrangler.json`). There on 2026-10-30, `OPTIONS /v1/swarms` and `OPTIONS /mcp` answered 204 with `*`, and `/mcp` exposed `mcp-protocol-version` and `mcp-session-id`.
- `POST /mcp` is a stateless streamable-HTTP MCP server (`WebStandardStreamableHTTPServerTransport` with `enableJsonResponse`, one server per request). `GET` and `DELETE` answer 405, because there are no sessions and no server-sent notifications. It has 13 tools: `swarms_list`, `swarm_get`, `swarm_answer`, `swarm_rounds`, `swarm_feed`, `swarms_search`, `swarm_create`, `swarm_pledge`, `swarm_contribute`, `swarm_budget`, `swarm_hand`, `swarm_pledge_status` and `swarm_wait`. Its instructions explain swarms, rounds, the three ways money comes in, notes and lent machines.
  - Funding over MCP: `swarm_pledge` uses the device flow below.
  - `swarm_contribute` without `hash` prepares a one-off transfer (`Operations.transfer`). It answers:
    - the swarm's wallet, which a swarm from before 0003 gets now;
    - the token's address and the memo, `Memo.memo`, the same one the page signs;
    - with `amount`, the `transferWithMemo` call data;
    - a link `/s/<id>?fund=transfer&token=&amount=&note=`, where the page sends it with Tempo Wallet and counts it.
    With `hash` it counts a transfer already sent (`Operations.contribute`). The server never sends money: the user's wallet does.
  - `swarm_budget` validates a daily budget and answers `/s/<id>?fund=budget&token=&amount=&note=` with the swarm's wallet and the key's limits. A budget key is generated by the swarm and approved with Tempo Wallet's `wallet_connect`. Budgets have no device flow yet (pledges have one, below), so the page approves them.
  - The contribution box reads those parameters (`asked` in `Contribute.tsx`). Checked on 2026-10-30:
    - The budget link opened the Daily budget tab with USDC.e, 1.000000 and the note.
    - The transfer link opened Send once with pathUSD, 0.500000 and the note.
    - The prepared call for 0.5 pathUSD decoded to `transferWithMemo(swarm wallet, 500000, keccak256("note:<id>:Add HTTP/2"))`. An `eth_call` of it from the test wallet succeeded, and nothing was sent. The server runs no model: the client's own model answers questions about the data by calling the tools, so reading costs nothing. An argument the SDK rejects comes back as an `isError` result with `MCP error -32602`. An operation's failure comes back as an `isError` result holding its problem JSON.
- Clients without a browser wallet pledge through Tempo Wallet's device flow. `device: true` on `POST /v1/swarms/:id/pledges` registers the pledge key's `wallet_connect` request with Tempo Wallet's device-code endpoint itself (`https://wallet.tempo.xyz/api/auth/device/register`, RFC 8628 with PKCE, as the gateway's `Keys.register` does; `Devices.register`) and stores the user code, the link, the interval, the expiry, the device code and the PKCE verifier in `pledge_devices` (migrations 0004 and 0007). The caller polls `GET /v1/swarms/:id/pledges/:pledge?wait=` (or `POST` with `{}`), which asks Tempo Wallet's `/token` and approves the returned key authorization as the browser path does. On 2026-10-31 the Worker registered such a request (a user code, a `wallet_connect?user_code=` link, 600 s, a 1 s interval) and polled it as pending; approving it needs a person and was not exercised.
  - Outcomes: 200 (or 202 for the `POST`) while the pledge is pending, 201 once it is active, 403 `access_denied` when the request was declined, and 410 `expired` past the expiry. A declined or expired pledge is forgotten, so later polls get 404.
  - `swarm_pledge` always uses the device flow, because an MCP client holds no wallet, and answers with the link to open.
  - Tempo Wallet hands out a device code's answer once, so a poll that gets no answer reads the pledge again and answers it active when another poller completed it a moment earlier.
  - Checked on 2026-10-30, locally:
    - A device pledge polled after its expiry answered 410 `expired`, and then 404.
    - A refusal, run against a mock gateway (a Node server whose `/api/keys/complete` answered pending and then 403), answered 403 `access_denied` over REST and over `swarm_pledge_status`.
    - A device pledge was never approved with a real wallet. Its success path is the same `activate` that two real browser-flow pledges went through: the web app's `/api` flow and `/v1`'s `keyAuthorization` flow.
- `swarm_wait` and `GET /v1/swarms/:id/wait` wait at most 55 s per call (`maxWait`), as does a pledge poll's `wait`. The MCP SDK client's default request timeout is 60 s (`DEFAULT_REQUEST_TIMEOUT_MSEC` in `@modelcontextprotocol/sdk` 1.32.2). A caller that wants to keep waiting calls again. This bounds only the wait: the swarm itself has no time limit.
- Search is a D1 FTS5 table, `search` (porter on `unicode61 remove_diacritics 2`, migration 0004). It indexes swarm titles and goals, notes and round reports, and ranks by `bm25` with titles weighted 2 and bodies 1. A query keeps its words minus stopwords, each quoted and joined with `OR`, so a query's punctuation can never reach FTS5 syntax. Like the list, search hides swarms that nothing funds: no approved pledge, no transfer or pull, and no active budget.
  - When rows are indexed: a swarm when it is created, a note when its pledge activates, its transfer is counted, its budget is approved or a budget with a note is pulled, and a report when its round ends (`Swarm` calls `Search.report`).
  - `Search.sync` fills in reports that are missing or changed. Reads of a swarm call it, and so does every search: an unscoped search checks the 5 most recent swarms with more rounds than indexed reports (`lagging`), which also covers rounds from before 0004.
  - Feed entries stay in the Durable Object. A search scoped to one swarm also scans that swarm's feed there (`Swarm.search`).
  - Checked on 2026-10-30 on a scratch D1 database on the Tempo account (`swarms-fts5-check`): created, migrated with 0001, 0002 and 0004, queried with `Search.query`'s exact SQL, then deleted. Porter stemming, `bm25` and `snippet` worked; production D1 refused read-only pragmas, so this was the check.
- D1 export does not support databases with virtual tables (Cloudflare's import and export docs: drop them, export, recreate them). Before `wrangler d1 export`, drop `search`. Afterwards, rebuild it from `swarms`, the notes of `pledges`, `contributions` and `budgets`, and `reports`, which holds every indexed report.
- `/docs` (`Docs.tsx`) documents the MCP server, the REST routes, the pledge flows, transfers and budgets, contributor hands, and the error codes. The home page's "Use it from code" section links to it.

## Contributor hands

- Anyone can lend a swarm their own machine as a nanocode hand. `POST /v1/swarms/:id/hands` (also `/api`, and the MCP tool `swarm_hand`) takes an optional `label` and answers the hand's `name`, `token` and `url`, plus both ways to attach:
  - `cli`: `nc hand '<url>' --token <token>` (nanocode 0.6.7), and `command`, the gateway's line that installs nanocode first.
  - `library`: a Node module that runs nanocode-ts's `Hand.connect` over its in-memory shell (`Connect.library`, release build-20f97e0, installed with `npm`).
  - `GET /v1/swarms/:id/hands` lists the issued hands and which are connected. The swarm page's "Connect your machine" box (`Connect.tsx`) issues one and shows both forms.
- A hand is an account hand of the operator key in the swarm's app (`POST /v1/hands?name=` with `Gateway-App: swarm-<id>`; see the gateway's AGENTS.md on account hands), so the lead and its explorers can use it in every round, whichever contribution pays.
- Hands issued before `upgrade`, under a swarm's old pool key, stop attaching, and so do all hands when the operator key changes; contributors issue new ones.
- Hand pricing belongs to the gateway and the hand SDK: an owner prices their own hand (`nc hand <url> --token <t> --pricing prices.json` with `{"payee","describe","rules":[{"paths","ops","usd"}]}`, or nanocode-ts `Hand.connect(…, { pricing: { payee, describe, price(operation) } })`), the gateway's hub charges the agent that made each priced call before it releases the reply (operation `hand.use` on `/mcp`, so this app's payer pays it like any MCP call, at the price as `amount`), and the gateway pays the payee in USDC.e. So Swarms keeps no prices, meters nothing and sends no payouts (the user's decision of 2026-10-31, after a first version that metered and paid hands from the swarm's wallet). It reads `GET /v1/hands`: `requests` (gateway 8c471aa: the operations the hub dispatched, the hand's environment probe included, never counted again on a replay) and, from gateway `feat/paid-hands` (agent 14's branch, not deployed on 2026-10-31), `pricing` (`payee`, `describe`), `charges` (`count`, `usd`, billed to this account's agents), `earned`, `paid` and `cap`. `Hands.terms` turns them into the price summary, charges and earnings that the Connect box, the hands API and the lead's prompt show (`test/hands.test.ts`). At each round's start `cap` sets every connected hand's cap to a fifth of what the round may spend with `POST /v1/hands/<name>/cap` `{ usd }`, which starts a new window each time, and a hand that joins mid-round gets the round's cap; it sends a cap only for hands whose listing has a `cap` field, so nothing reaches a gateway without caps.
- Lent hands are paid over MPP channels to their owners (2026-10-31, with gateway `feat/mpp-hand-billing`, not deployed that day): for a hand charge the gateway's payer request carries the owner's OUSD session challenge first, with `recipient` (the owner's address) and `hand`, and each channel snapshot names its `payee`. `Swarm.charge` then tries the swarm's wallet on a channel of its own to that owner first (source `hand:<payee>`, its mppx store `mppx:hand:<payee>:`, opened with 0.05 or the price, whichever is more, and topped up by 0.05, smaller than the gateway channel's 0.1 because it can pay only that owner), and only when the wallet cannot (no OUSD left, a USDC.e owner, a refused credential) falls back to the usual sources paying the gateway's challenge, which the gateway turns into its payout to the owner; a MACH pledge always falls back, because MACH cannot reach an owner. `Payer.offer` takes the recipient and now hands mppx a 402 with only the chosen challenge: before, a wallet paying the gateway's OUSD challenge on a hand charge would have signed the owner's OUSD challenge, the first in the list. The owner channels count in `pool_spent`, not in what a round may spend, since their deposits pay only their owner. At done `settle` closes them with `requestClose` from the wallet (no cooperative close: the gateway's `kv/get` route takes only its own channels), which the gateway's close supervision answers, and the refund waits for every such channel's deposit to reach 0 (`closing:hand:<payee>`). `Hands.terms` adds `channels` (what the owner was paid over channels and how much settled) and the price's currency, which the Connect box and `Lent` in the OpenAPI document show. The fallback through a MACH pledge was not run.
- Names are `<slug of the label>-<6 random hex>`, recorded in D1 `hands` (migration 0006) under `(swarm, name)` with insert-or-ignore and up to three tries, and the swarm also refuses a name the gateway already lists. They must not collide: the gateway hands out the same secret when the same name is minted again under one key, so a repeated name would give one contributor's token to another. A swarm takes at most 32 hands, a number chosen without measurement.

## Development

- `pnpm dev` runs the Worker and the page. Set `SWARMS_STATE=<dir>` to keep local Durable Object and D1 state there, and `SWARMS_GATEWAY=<url>` to use a local gateway: only then, and only under `vite` serve, the Worker's `GATEWAY_URL` is that URL and `global_fetch_strictly_public` is off, because the flag sends fetches to the public internet, which a local gateway is not on. Builds and deploys keep `wrangler.jsonc` as it is. `pnpm db:migrate:local` (add `--persist-to <dir>` with `SWARMS_STATE`) applies `migrations/`. `.dev.vars` needs `SWARMS_SECRET`, `SWARMS_GATEWAY_KEY` and `SWARMS_URL`, a public URL of the dev server, because the gateway calls the pay route there: `cloudflared tunnel --url http://localhost:<port> --http-host-header localhost` (vite answers only its own host names, so the tunnel rewrites the Host header).
- `pnpm check` type-checks the Worker and the page. `pnpm build` builds both. `pnpm exec wrangler dev -c dist/swarms/wrangler.json` runs the build, where CORS preflights behave as deployed.
- Deploy: set `SWARMS_SECRET` and `SWARMS_GATEWAY_KEY` with `wrangler secret put`, then `pnpm db:migrate` (0007 only adds columns), then `pnpm deploy`. The gateway must have agent payers (82d56b6) and public reads (5b5c47d); cooperative closes need its session account (70818b8). The Worker reaches the gateway over the public internet (`global_fetch_strictly_public`), as a third party would.
